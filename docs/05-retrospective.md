# 05｜复盘：难点、收获与下一步

## 最难的问题

**一份检索结果“看起来相关”，不等于可以回答。** 当合成 D01/D02 都宣称适用于正式员工，却分别给出 30 个自然日与 15 个自然日时，只依据最高分片段或最新日期给出单一数字并不可靠。实现中将检索结果与全文分开，保留版本、适用范围与主张元数据；对已发现的冲突强制双文档引用、禁止擅选规则。`top_k=1` 场景也添加相同主张的冲突候选，降低“只取最相似一条”掩盖分歧的风险。

另一个难点是**真实模型规划与离线测试不能混为一谈**。采用可替换的 `DecisionModel` 接口，真实 API 每步决策，离线策略只是能复现复杂路径的测试替身；两者共用工具、引用守卫和 Trace，既满足可执行要求又不粉饰效果。

## 学到的内容

- RAG 的根本问题是证据闭环：相关性、原文支持、制度效力与置信边界需要分开处理。
- LangGraph 最有价值的地方在于把工具观察返回决策节点，而不是框架名字本身。
- 测试“模型是否能拒答或追问”与测试“模型是否能说对”同样重要。
- 仅看引用条数会产生虚假的可信感：必须至少检查 doc ID 是否已读、引文是否逐字存在、数字是否有原文支撑。

## 已知局限和具体后续计划

1. **真实模型测试**：接入自己的模型账号，在 `--mode llm` 上重复六类验收，尤其确认 LLM 是否自发补检索、查冲突与进行上下文改写；报告真实失败率而不是只看 demo。
2. **提升召回**：接入高校 RAG 的 BGE-M3、Milvus Dense+Sparse 与 Reranker，原始索引保留稳定 doc ID 和版本/生效日期；评估 Recall@k 与文档冲突检出率。
3. **冲突推理**：给每个规则补充辖区、部门、覆盖群体、文档上下位优先级及显式 supersedes 链接；在范围重叠与版本替代上建立独立规则评估。
4. **上线前安全**：租户隔离、文档可见权限、敏感文本屏蔽、提示词注入红队测试、审计与持续监测。
5. **可观测性**：结构化记录模型调用耗时、token 花费、每步检索排序、失败原因；用户界面中点击引用跳转到文档原文并高亮片段。

当前项目故意优先完成核心链路和验收证据，而不把界面、部署、多 Agent 作为纸面加分项。
