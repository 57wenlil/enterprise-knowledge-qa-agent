# 01｜需求与成功标准

## 用户与痛点

企业员工需要根据散落在 FAQ、制度文档中的规定快速找答案。普通问答系统容易遇到：问题改写导致检索失败、跨文档冲突却只返回一个答案、只引用检索摘要而非原文、多轮追问丢失主题、工具失败时仍编造回答。

## 范围

用户输入自然语言问题和可选对话历史；本项目持有 6 份带稳定文档 ID、版本日期、适用范围与原文的**合成**制度/FAQ，采用可离线复现的检索工具。交付 `answer`、`citations`（`doc_id`+逐字`quote`+版本日期等）、`missing_information`、`status`、`trace`。

包括：检索、按 ID 全文读取、Agent 自主动作选择、冲突确认、上下文追问、资料外问题拒答、工具异常与执行上限。排除：线上部署、多 Agent、企业内部权限治理、OCR、大规模向量建库、生产级安全隔离。可选的模型和 LangGraph 已留接入路径。

## 可执行的成功标准

1. 明确答案：至少经过检索与原文读取；答案引用可逐字在原文中找到。
2. 制度冲突：D01“30个自然日”和 D02“15个自然日”同范围、无法确定优先级；读取双方资料，返回冲突说明和确认问题，而不是自行选 15 天。
3. 资料外问题：找不到可靠资料，输出 `insufficient_evidence`，引用为空。
4. 同义改写：如“入职一年有几天带薪假”，可命中 D03 年假。
5. 上下文追问：在“年假几天”后问“那提前多久申请”，可引用 D03 的“提前3个工作日”。
6. 工具故障：模拟检索/读取失败，留有失败 Trace，返回 `error`，不编造答案。
7. 至少两条不同工具执行路径，逐步记录 `step/action/arguments/result_summary/reason_summary`。
8. 步数上限触发时明确 `incomplete`；引用不存在、错引、乱报数量均被阻断。
9. 一条 `python -m app.cli` 命令可运行，不靠截图代替源码。

## 评估边界

离线 demo 能验证程序闭环，不是大模型自行规划的质量证据。真实 `--mode llm` 使用每轮模型产生的 JSON 动作；评估其决策、改写、证据甄别需要有效的模型 API Key。真实制度必须另行考虑权限、失效、例外以及法律/财务部门的最终裁定。
